# マルチエージェント開発の運用ガイド

対象読者: この開発体制に参加する AI エージェント(設計担当・実装担当とも)と人間。
最終更新: 2026-07-10。本書は pelican2 で確立した運用の記述であり、実績 20 ウェーブ・
60+ WP で検証済み。

## 0. 体制(誰が何をするか)

| 役割 | 担当 | 責任 |
|------|------|------|
| 意思決定 | ユーザー(enjoyoriori) | 方向決定・凍結文書の改訂承認・トレードオフの選択 |
| シニアエンジニア | Claude(対話セッション) | 設計文書・WP 指示書・レビュー・マージ・検証・進行管理。**実装は書かない** |
| 実装 / 監査 / 敵対レビュー | codex(ヘッドレス起動) | WP の実装、コードベース監査、設計への敵対的批評 |

原則: **設計と実装の分離**。シニアは「何を・なぜ」を文書化し、実装エージェントは
「どうやって」を担う。実装エージェントは設計から逸脱せず、矛盾を見つけたら
実装せずに報告する(BLOCKED.md)。

## 1. 作業の単位: WP(Work Package)

- **1 WP = 1 ブランチ(`agent/wpNN-slug`)= 1 worktree = 1 マージ**
- WP は `docs/implementation_plan.md` に登録(手順・依存・**受け入れ基準**)。
  **受け入れ基準 = マージ基準**(交渉の余地なし)
- 実装エージェントには **goal ファイル**(自己完結の依頼書)を渡す。内容:
  worktree パスとブランチ / 必読文書 / 要点の再掲 / 並走注意(専有領域)/
  ビルド・テストコマンド / 完了条件 / 終了時の規約
- ブランチは統合ブランチ(現在 `codex/rendering-phase1-refactor`)から切る。
  WP 同士のスタック禁止

## 2. ウェーブ並列

独立な WP を 3〜4 本同時に走らせる。事故防止の規約:

- **専有領域を事前に宣言**(implementation_plan のウェーブ表): 各 WP が触って
  よいディレクトリを列挙し、goal に「触ってはいけない場所」を明記
- 交差が避けられないファイル(gamecontext・rpcserver・test/CMakeLists)は
  「末尾追記」等の作法を指示し、**統合時にシニアが競合を解決**
- golden テストを複数 WP が追加する場合、各 WP で
  `python test/golden_inventory.py --repo-root . --update` を実行し、**case/file/hash/trace
  membership の inventory diff を明示**する。統合時は再生成して交差差分を確認する

## 3. codex の起動標準

```powershell
# 親シェルで環境を設定してから起動(PS 5.1 に -Environment は無い)
$env:CODEX_HOME = 'C:\Users\enjoy\.codex-alt'   # アカウント切替時のみ
Start-Process -FilePath 'C:\nvm4w\nodejs\codex.cmd' `
  -ArgumentList @('exec', '-C', '"<worktree>"', '-s', 'danger-full-access',
                  '-m', 'gpt-5.6-sol', '-c', 'model_reasoning_effort=xhigh',
                  '"<goal ファイルを読んで完遂せよ>"') `
  -RedirectStandardOutput <run.log> -RedirectStandardError <err.log> -WindowStyle Hidden
```

- モデル: **gpt-5.6-sol / xhigh / 通常速度**(service_tier 指定なし)。
  情報ソースを増やすリサーチは effort **ultra**
- **`codex` ではなく `C:\nvm4w\nodejs\codex.cmd` を直接指定**(PowerShell の
  実行ポリシーが .ps1 シムをブロックする)
- 引数のスペース含む値は個別にクォート(Start-Process の引数分解事故防止)
- **アカウント 2 系統**: プライマリ = `~/.codex`(desktop 版と共有 — 触らない)。
  上限(サブスク枠・ローリングリセット)に当たったら
  `CODEX_HOME=C:\Users\enjoy\.codex-alt` で第 2 アカウントに切替
- 完了判定: err.log 末尾の `tokens used`。進捗はログサイズと最終書込時刻で見る。
  **実行中にポーリングで張り付かない**(ユーザーが聞いたら確認する)

## 4. 設計の敵対レビューループ(品質の要)

設計文書は実装前に必ずこのループを通す:

```
Claude が設計ドラフト(vN)
  → codex に敵対的批評を依頼(「忖度なし・根拠(ファイル:行)必須」を明示。
     実コードとの突き合わせ・業界前例比較・「他エンジンがやらなかった選択と
     その理由の考察」を依頼内容に含める)
  → 判定(Accept / 条件付き / Reject)
  → Claude が受理・反駁を仕分けて v(N+1) へ改稿
  → 再レビュー(主目的 =「指摘の解消照合」+「改稿が作った新しい穴」)
  → Accept で確定 → WP 化
```

- レビューは `docs/design_reviews/YYYY-MM-DD_<topic>_codex.md` に**リポジトリ収録**
  (レビュー条件はそのまま WP の受け入れテストになる)
- 実績: マテリアル設計 v1→v1.2、ECS 設計 v1(Reject)→v2(条件付き)→v2.1(確定)。
  いずれも初稿の急所(実装不可能な仕様・既存契約の破壊・ABA 復活)を実装前に検出
- codex は「図書館員」としても優秀 — 技術的疑問(前例の有無・ライブラリの制限)を
  依頼に同梱してよい。不確かな場合は不確かと明記させる

## 5. レビュー・マージのゲート(シニアの仕事)

マージ前に必ず全部やる:

1. diff の専有領域チェック(規約違反がないか)
2. マージ(競合はシニアが解決)→ フルビルド → **ctest 全件**
3. **golden inventory を GPU なしで照合**
   (`python test/golden_inventory.py --repo-root .`)してから、golden は verbose で
   SKIP 検査(`ctest -R golden -V` で SKIP/例外の握りを確認 — 「全部 passed」だけを
   信じない。過去に本物のプランナエラーが SKIP に化けて素通りした)
4. player の起動スモーク(8 秒)
5. push → worktree/ブランチ削除 → 進捗メモリ更新

削除系 WP の受け入れは「**消しても何も変わらない**」の機械的証明
(テスト・golden・player 完全無変化)。

## 6. 実装エージェントの鉄則(goal に毎回書く)

1. **ビルドを早期に開始**。何時間も編集だけ続けない(ビルド未着手のまま停滞した
   エージェントは殺して、新セッションに「worktree の diff を引き継ぎ最小変更で
   完遂」と指示する — diff が状態を持つのでエージェントは使い捨て可能)
2. **常駐プロセスを起動したら必ず停止してから終了**(dev サーバ放置で
   ラッパーが 4 時間ハングした実績)
3. 判断不能なら実装せず **BLOCKED.md** を書いて終了。設計の勝手な再解釈は禁止
4. 他の checkout・worktree のブランチを切り替えない
5. スコープ外に手を出さない(「ついで」の修正は別 WP)

## 7. コードベースの不変規約(全エージェント共通)

- **ランタイムは v1 形式だけを読む**。旧形式の変換は外部ツール —
  新旧両対応の受理コードを足すことは規約違反(2026-07-08 決定)
- 凍結文書([PF]/[PFW] 等)の変更は版数改訂 + ユーザー承認が必須
- 決定性を壊さない(wall clock / std::rand / random_device を判定に使わない)
- フレームを跨いでコンポーネントへの生ポインタを保持しない(ID + resolve)
- バイナリ fixture は `.gitattributes` で保護(CRLF 変換が sha256 を壊す)
- ログは quill(stdout は rpc プロトコル専用)

## 8. ファイルの地図

| 場所 | 内容 |
|------|------|
| `docs/implementation_plan.md` | WP 詳細・受け入れ基準・ウェーブ表(§0 = 共通規則) |
| `docs/design_*.md` | 設計文書(README.md が索引・凍結状態つき) |
| `docs/design_reviews/` | codex の監査・敵対レビュー(一次資料として恒久保存) |
| `docs/adding_features.md` | 機能追加レシピ集 |
| goal ファイル | セッションの scratchpad(渡すときは絶対パスで) |

## 9. この運用が機能する理由(新参エージェントへ)

- **契約(受け入れ基準・専有領域・形式)を文書に固定し、会話に依存しない** —
  エージェントは使い捨てでも、diff と文書が状態を持つ
- **検証が機械的**(golden・ctest・決定性)なので「動いた気がする」が存在しない
- **敵対レビューをコストでなく標準工程にする** — 初稿の欠陥は実装前に潰すのが
  最安。批評には必ず根拠を要求し、受理・反駁の判断はシニアが行う
- 疑わしいときは止まって報告する方が、黙って進めるより常に安い
